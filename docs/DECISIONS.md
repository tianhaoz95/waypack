# Decisions & deviations from the design doc

The design (`docs/design.md`) was originally written with the working name *Tripfold* (now updated to *Waypack*). Deviations are recorded here, newest last.

| # | Decision | Why |
|---|---|---|
| 1 | **Name: Waypack** (waypoints + packed to go). App IDs `com.hejitech.waypack`; domain placeholder `waypack.app`; MCP at `mcp.waypack.app/mcp`; SDK path `/__waypack/sdk/v1/waypack.js`; global `window.Waypack`; npm scope `@waypack/*`. | Owner asked for a real name under `com.hejitech.*`. Search-and-replace `waypack`/`Waypack` to rename. |
| 2 | **Local-first, deploy-ready.** Everything runs locally (wrangler dev, `supabase start`, Docker tiler, Flutter simulator). No cloud resources created; `docs/DEPLOY.md` lists the secrets/commands. | Owner choice. |
| 3 | **Tiler on Cloudflare Containers** (`services/tiler`), invoked from the Worker's queue consumer via a Durable-Object-backed container binding. Dockerfile is portable to Fly/Cloud Run. | One vendor with Worker/R2/Queues. |
| 4 | **Ajv runs at build time** (standalone code, bundled with esbuild) instead of at runtime. | Workers forbid `new Function`/`eval`. Same validator runs in CLI, Worker and browser. |
| 5 | **MapLibre GL JS v6** is ESM-only and spawns a separate worker module. The SDK ships `waypack.js` (IIFE) **plus** `waypack-worker.js` and calls `setWorkerUrl()`. | Keeps everything same-origin and offline; satisfies CSP `worker-src 'self' blob:`. |
| 6 | **Multiple map extracts → one basemap source** via a custom `wpk://` protocol that serves each tile from the first PMTiles archive covering it. | Avoids duplicating ~100 style layers per extract. |
| 7 | **Glyphs:** Protomaps Noto Sans fontstacks (~14 MB) ship with the SDK. CJK/Hangul labels are rendered from device fonts (`localIdeographFontFamily`), so they work offline without glyph PBFs. | Offline labels without a 100 MB font payload. |
| 8 | Basemap max zoom is **15** (Protomaps builds stop there); `max_zoom: 16` in a manifest is accepted but clamped by the tiler, and MapLibre overzooms. | Matches the data. |
| 9 | **Planet source:** daily builds at `https://build.protomaps.com/YYYYMMDD.pmtiles` (listed at `build-metadata.protomaps.dev/builds.json`). Dev/preview read them directly via HTTP range; production mirrors monthly to R2 (`services/tiler` `mirror` job) per design §6.6. | Open question 5: mirror for production, direct for dev. Check Protomaps' usage terms before relying on direct reads in production. |
| 10 | `waypack preview` **proxies** range requests to the planet so the page stays same-origin under the real CSP. | Faithful preview of in-app behavior. |
| 11 | Manifest gains optional **`nav_app`** (`google`/`apple`) and place **`hours`/`cost`**. Extra properties are allowed by schema. | Interview asks for preferred navigation app; template displays hours/cost. Additive, non-breaking. |
| 12 | Routing/geocoding default provider is **OpenRouteService** (per design), behind an interface; the Worker also supports a keyless **dev mode** (Nominatim + OSRM demo servers) when `ORS_API_KEY` is unset. | Lets the full flow run locally without keys. Public demo servers are not for production. |
| 13 | Local server auth: per-launch token passed once as `?k=` on the first navigation, exchanged for an `HttpOnly; SameSite=Strict` cookie scoped to the loopback origin. | The SDK uses absolute `/__waypack/...` paths, so a path-prefix token wouldn't work. |
| 14 | **MCP endpoint is a small hand-written stateless JSON-RPC server** (`services/mcp/src/mcp/protocol.ts`, Streamable HTTP with JSON responses) instead of `agents`' `McpAgent`. | `agents@0.26` pins `@modelcontextprotocol/sdk@1.30.0` while the SDK is migrating to v2; a tools-only server needs ~150 lines, has no Durable Object/session state, and is fully unit-tested. OAuth is still `@cloudflare/workers-oauth-provider`. |
| 15 | ~~**MCP sign-in = Supabase email OTP (6-digit code), verified server-side** on the Worker's `/authorize` page, plus a 30-day signed session cookie so later connections are one tap. Apple/Google sign-in exist in the app; accounts match by email.~~ **Superseded by #29.** | No client JS, works in every browser the agent opens, and identical to the app's sign-in. |
| 16 | **Uploads and downloads go through the Worker** with HMAC-signed, expiring URLs (`PUT /upload/:id`, `GET /files/<key>` with Range) instead of R2 S3 presigned URLs. `download-urls` lives in the Worker (`GET /api/trips/:id/download`), not a Supabase Edge Function. | Works identically in `wrangler dev` (no S3 endpoint locally) and production; one place owns R2 access. Bundles ≤ 25 MB fit Worker request limits. |
| 17 | Extracts retired by a manifest change are marked `skipped`; `expired` is reserved for the 30-day post-trip expiry, which entitled users can re-cut on demand when downloading. | Keeps on-demand re-cut from resurrecting areas the trip no longer uses. |
| 18 | Local Supabase uses ports **554xx** (`supabase/config.toml`). | Another local Supabase project on this machine owns the default 543xx ports. |
| 19 | ~~RevenueCat entitlement id **`pro`**; products **`waypack_annual`**, **`waypack_lifetime`**. Webhook is idempotent on event id and, when `REVENUECAT_API_KEY` is set, refreshes from RevenueCat's subscriber API (authoritative) instead of trusting event order.~~ **Superseded by #25.** | Design §11, renamed. |
| 20 | App local server uses **`dart:io` `HttpServer`** directly instead of `shelf`. | Needs only static files + Range + cookies; fewer deps, easier to audit the security checks. |
| 21 | The SDK ships in the app as **one asset (`assets/sdk.zip`)**, unpacked to app support storage once per SDK version. | Flutter assets aren't recursive; ~1,000 glyph files with spaces in paths are awkward to declare. |
| 22 | **`flutter_inappwebview 6.2.0-beta.3`** — the stable 6.1.5 Android plugin fails on AGP 9 (`proguard-android.txt`). | Move to stable 6.2.x when released. |
| 23 | Local downloads record the **owner (Supabase user id)**; another account signing in on the same device doesn't see them. | Privacy on shared devices. |
| 24 | Native "Map" overlay is a built-in SDK page (`assets/app/map.html`) served at `/t/{trip}/__waypack_map.html`, not a native map widget. | Same offline renderer and styling as bundles, zero extra native map deps. |
| 25 | **Billing moves to the web with Stripe; the mobile apps are free viewers.** The account portal (`site/account.html`) offers Stripe Checkout (Pro annual subscription; optional lifetime one-time price) and the Stripe Customer Portal. The Worker's `/stripe/webhook` verifies signatures, deduplicates on event id, and writes `entitlements` (`source = 'stripe'`). RevenueCat, the in-app paywall and `purchases_flutter` were removed. | Owner direction (2026-10-03): what costs money is the cloud storage + map extraction behind MCP, so users subscribe on the web. App Store Guideline 3.1.3(f) (free companion to a paid web service) requires **no purchase UI or calls to action in the app**: the app only shows the current plan. |
| 26 | **One origin, one deploy**: the Worker serves the landing page + portal (`site/`, Workers static assets), the app/portal API, OAuth and MCP at `https://waypack.app` (MCP URL `https://waypack.app/mcp`). | Simplest deployment; the portal's session cookie and the MCP authorize page share one sign-in. |
| 27 | Portal auth: email code → signed **HttpOnly SameSite=Lax session cookie** (same cookie as the MCP authorize page). Cookie-authenticated mutations require an `X-Waypack: 1` header plus a same-origin `Origin`, so cross-site forms and scripts can't trigger them. | CSRF protection without tokens; the API is never CORS-enabled. |
| 28 | Upgrading cuts offline maps for trips already published on the free plan (on the Stripe webhook, and lazily when the app requests a download). | Otherwise users would need to ask their agent to re-publish after paying. |
| 29 | **Sign in with Google or Apple only. No email/password and no email codes, anywhere.** App: native Sign in with Apple sheet on iOS (`signInWithIdToken` + nonce, so no rotating secret is needed for the app) and a system auth pop-up (`flutter_web_auth_2` + Supabase PKCE) for Google, and for Apple on Android. Web portal and MCP authorize page: Worker-side PKCE (`/auth/start` → Supabase → `/auth/callback`) with a browser-bound state cookie (login-CSRF), then the shared session cookie. | Owner direction (2026-10-03): one-tap sign-in, minimal setup, no email sign-in. Apple is required next to Google in the iOS app (App Store guideline 4.8), and must also be on the web so Apple "Hide My Email" users can reach the portal and connect agents. |
| 30 | **Dev-only sign-in** for local development and automated tests: `POST /api/auth/dev` and a form on the authorize page, which the Worker refuses unless `ENVIRONMENT=development` on a loopback `PUBLIC_URL`. The app shows it only in builds with `--dart-define=DEV_SIGN_IN=true`. It mints a real Supabase session via the admin API. | Real Google/Apple can't run in CI or on this machine without your credentials. Production has the Email provider disabled. |
| 31 | Email + password was tried (commit `eb130a2`) and **reverted** in favor of #29 (Google + Apple). | Owner decision (2026-10-03) after comparing costs: Google/Apple sign-in is $0 per user (Apple needs the $99/yr developer membership the iOS app requires anyway). It sends no email and leaves password attacks, bot sign-ups and credential stuffing to Google/Apple, whereas email + password exposes the password-reset email to abuse (cost and sender reputation). |
| 32 | **Add to calendar without calendar permissions.** The app uses `add_2_calendar` (system "new event" sheet: the user confirms each event; iOS asks at most once for write-only "add events" access and the app never reads the calendar). Google Calendar uses a `calendar.google.com/calendar/render` link with local wall-clock times plus `ctz`, so the event lands at the right local time whatever the phone's time zone. Without `end_time`, an event runs until the next timed item (max 3 h), or 1 h for the day's last item. | Works offline for Apple; no read access to the calendar; Google's API would need OAuth scopes for a one-off add. |
| 33 | **Themes are data, not code**: `manifest.theme` = preset (CSS variable set in `assets/theme.css`) + `scene` (layers drawn by `assets/scene.js` as inline SVG). Agents may still restyle freely. | Agents get a destination-specific look by choosing words, not by writing SVG; the app can read the same accent to tint native screens; stays fully offline. |
| 34 | **Responsive breakpoints** in the template: 760px (two columns) and 1100px (side rail + pinned map). The validator's wide-screen, theme and calendar checks are warnings, not errors. | Future iPad/desktop clients; warnings keep older bundles valid. |
| 35 | **Mac app = the same Flutter app built for macOS**, shipped as a **notarized DMG from the site**, not the Mac App Store. Free viewer, no purchases (same rule as iOS). | Owner decision (2026-10-04). One codebase; all plugins except `add_2_calendar` already support macOS. The DMG avoids App Store review for the Mac. |
| 36 | DMGs live in R2 (`releases/mac/Waypack-<version>.dmg` + `latest.json`) and are served by the Worker at `/download/mac` (302 to the versioned file, immutable caching, Range support). | Workers static assets cap files at 25 MiB; the DMG is ~36 MB. Same bucket and serving code as trip downloads; one deploy. |
| 37 | Mac Add to calendar opens Calendar.app with a one-event `.ics`, since macOS has no system "new event" sheet for third-party apps without calendar access. SDK `Waypack.platform()` gains `"macos"` (additive), which picks Apple Maps / Apple Calendar by default. | Works offline and needs no calendar permission. Existing bundles keep working: unknown platforms fall back to the browser wording. |
| 38 | No Mac auto-updater yet. | Ship first; add Sparkle (EdDSA-signed appcast next to `latest.json`) once there are users to update. |
| 39 | **Live previews.** Agents push work-in-progress bundles (`push_preview`, changed files only) to a per-trip **draft**; the user opens an unguessable link (`/t/<32-char token>/`) on any device and open pages reload themselves on each push (keeping tab and scroll). `publish_preview` turns the draft into a normal trip version through the same pipeline as uploads. Drafts never reach the app, never count toward trip limits and never cut offline maps (pages use the online basemap through a same-origin Range proxy). | Owner direction (2026-10-04): let the user watch and redirect the plan while it's built, from any client, including chat agents with no shell. |
| 40 | **Previews are served from a separate origin** (`PREVIEW_URL`, e.g. `waypackpreview.com`; `http://localhost:8787` locally vs `127.0.0.1` for the site). The Worker routes by host before OAuth (`run_worker_first: true`): the preview origin serves only previews, the SDK and the tile proxy, with the app's CSP + `frame-ancestors 'none'`, `Referrer-Policy: no-referrer` (the token never leaks to linked sites) and no cookies. | Previews are agent-written HTML; on the main origin they could act with the viewer's session. |
| 41 | Draft storage: content-addressed blobs in R2 (`previews/<user>/<id>/blobs/<sha256>`) + a `path → sha256` map in `trip_previews`. A push writes new blobs, validates the whole draft (issues reported, never blocking), then swaps the map with a conditional update on `rev` (concurrent pushes merge instead of overwriting). Blobs used by neither the current nor the previous revision are deleted. | Atomic for viewers, cheap incremental pushes, no R2 copy operations needed. |
| 42 | Live reload = polling `/__waypack/preview/<token>/state` every 3 s while the tab is visible (15 s after 30 quiet minutes), not WebSockets. | Simple and stateless; a Durable Object push channel can replace it if previews get heavy use. Workers KV is unsuitable (up to 60 s stale). |
| 43 | Preview limits: 4 MB per `push_preview` call (zip path via `create_upload {preview: true}` for larger), 25 MB / 2,000 files per draft, 10 open drafts per account, 20 pushes/min and 600/day, expiry 14 days after the last push (cron). | Bound abuse of free HTML hosting; generous for real plans (examples are 0.1–1 MB). |
| 44 | **Public, remixable trips.** `share_trip` snapshots a published version into its own content-addressed blobs (`shares/<user>/<id>/`) served read-only on the preview origin at `/t/<token>/`, with a "Plan this trip" button to `PUBLIC_URL/remix/<token>`. The remix page builds a prompt for the viewer's own agent ("Open in Claude" via `claude.ai/new?q=`, or copy); the agent reads the plan with `get_shared_trip` (manifest without route geometry + page text). One live share per trip: sharing again moves the same link to the current version. Deleting the trip stops sharing it. | Owner direction (2026-10-04): growth loop where every shared trip can turn into a new one; agents plan better from a proven trip. |
| 45 | Shares are **redacted automatically** (booking/confirmation/PNR-style codes containing a digit become `••••`; the manifest's `trip_id` is dropped), and the owner is warned that names, private numbers and notes are **not** detected. Agents can share a cleaned copy (`share_trip { files }`). | Regex redaction is a safety net, not a guarantee; the explicit confirm + cleaned-copy path covers the rest. |
| 46 | Remix count = `get_shared_trip` reads (an atomic `increment_remix` SQL function), not published remixes. Shared pages stay `noindex`. Owners are never shown to viewers. | Counting publishes would need a manifest field linking trips; reads are a good enough signal for now. Indexing and author credit can come with a gallery later. |
| 47 | **Travel companions.** The owner's invite link (`/join/<24-char code>`, reusable, 14 days, can be turned off) lets companions join after signing in; they become viewers (`trip_members`): the trip appears in their app and portal ("Shared with you by …"), they can download it with the owner's offline maps, and they can leave. They can't change, share, delete or see other companions; the owner can remove them. Max 8 per trip. Not exposed as MCP tools (owners manage companions in the app or portal). | Owner direction (2026-10-04): the whole group should have the plan, not one phone. |
| 48 | **Offline handoff = QR + local HTTP**, not Multipeer Connectivity / Nearby Connections. The sender zips its stored version and serves it on the LAN (`HttpServer` on 0.0.0.0, random port) behind an 8-character code, for 15 minutes or until the screen closes, shutting down after 20 wrong codes. The QR carries the addresses, the code and the SHA-256 of the offer; the receiver verifies the offer, then every file, and installs atomically like a download (`received_nearby`). Typed address + code works without a camera (Mac, simulators). | Works across iPhone, Android and Mac (Apple's and Google's P2P frameworks don't interoperate); a Personal Hotspot gives a LAN with no signal; reuses the app's existing download/install path. |
| 49 | **Offline trip assistant on-device only.** One Dart interface (`lib/assistant/engine.dart`) with one channel protocol implemented natively: Apple Foundation Models on iOS/iPadOS/macOS 26+ (`WaypackAssistant.swift`, shared by both Xcode targets) and Gemini Nano via ML Kit's GenAI Prompt API 1.0.0-beta4 on Android (`WaypackAssistant.kt`; minSdk raised 24 → 26). Devices with neither get a plain "not available on this device yet" screen. A downloadable open model (Qwen on LiteRT-LM) slots in later as another `AssistantEngine` in `AssistantEngines.candidates()`; the picker already supports "downloadable" engines and keeps the most helpful reason. | Owner direction (2026-10-04). Answers must work with zero signal; no server, no cost per question, nothing leaves the device. |
| 50 | **Small-model grounding is done in Dart, not by the model.** Each question gets a compact brief (≤ 7,000 chars ≈ 1,800 tokens; both models have ~4k context): now/next in the trip's time zone, today (+ tomorrow for time questions, + named days), "most relevant" places (named in the question or matching its category, with phone/address/hours), other places with straight-line distance + direction from the GPS fix, emergency contacts (first for urgent questions, never trimmed) and guide passages (kept with their headings; plan-B questions also match backup words). The question appears before and after the notes; instructions are plain and short. Tuned against Apple's real model with `apps/mobile/tool/assistant_eval/` (11 cases, expected facts): 11/11 on repeated runs. | Small models echo ALL-CAPS headings, grab the first number they see and over-apply rules ("give the emergency number first" on every answer); these were measured and fixed, not guessed. Residual risk: paraphrase drift (e.g. "sledding" where the plan said "gentle play"), hence the on-screen "Answers can be wrong" note. |
| 51 | **Revisions are agent-led, not modeled.** No schema for "options" or "bookings": the agent decides what an update ("we booked X", "add a day", "the road is closed") implies. The product makes that cheap and safe: the skill's generic "Updating an existing trip" procedure (find → start from the latest files → change everything affected, keep the rest → preview with a note → publish on approval); `get_trip` returns the latest published `manifest.json` + `index.html` (other files on request, whole-zip `download_url` for CLI agents); `push_preview { trip_id }` starts the preview as a copy of the latest published version (re-based if a newer one was published elsewhere), so agents push only changed files; `note` tells viewers what changed ("Updated: …" toast, portal). | Owner direction (2026-10-04): updates have endless shapes and agent judgment improves with models; a structured options model would cap both. |
| 52 | **The assistant sees the whole plan, whatever its keys.** Manifest keys are suggestions for agents (the app acts on the ones it knows), not a description every trip must fit, so the assistant doesn't depend on them: `PlanIndex` walks the entire manifest generically (any key, nested lists split into entries, ids/coordinates hidden, coordinates under any spelling kept for distances) plus the page's passages with their section paths, and searches it (BM25 + name boost + question-word expansion such as fever → medical/hospital). Apple Foundation Models get a `searchPlan` tool (the model searches as it needs; Swift calls back into Dart for results); Gemini Nano has no tool calling in the Prompt API, so the same search runs up front and pre-fills the notes. Computed facts stay computed: now/next in the trip time zone, today's schedule, GPS distance/direction. Measured with `tool/assistant_eval/run.sh` (in-app, real model, 14 cases incl. 3 about keys the app has never seen): 14/14 with tool calling and 14/14 with pre-filled results (both on Apple's model). | Owner direction (2026-10-04): the assistant should get all information, as context or through a lookup tool. ~4k-token models can't take the whole plan, so search is the way to "all information"; the eval found and fixed distraction failures (raw route numbers, the wrong backup plan) by returning fewer, location-filtered results. |
| 53 | **Downloadable fallback model on Android: Qwen3-1.7B (dynamic int4, 977 MB) on LiteRT-LM 0.17.1** (`WaypackLocalModel.kt`, channel `waypack/assistant/litert`, same protocol as the system engines). Dart tries Gemini Nano first, then this one; a ready engine beats one that needs a download. Offered on 64-bit phones with ≥ 5.5 GB RAM (`deviceTooSmall` otherwise). The file is pinned to a Hugging Face commit, downloaded in-app with HTTP Range resume, checked for free space, and verified by SHA-256 before use. It runs on the GPU when LiteRT can use it, else on the CPU, thinking turned off, instructions at the top of the user turn (this model's chat template rejects a system message), and it is unloaded after 3 idle minutes. | Gemini Nano covers few phones (e.g. not the owner's OnePlus Open). Eval on the Mac's CPU with the same 14 assistant prompts: Qwen3-1.7B int4 10/14, ~14 s per answer; Qwen3.5-2B int8 (2.1 GB) got stuck repeating itself on several answers and was slower, so it was rejected. Apache 2.0, ungated. Costs: about 22 MB of native code per ABI in the APK. Follow-ups: test on a real phone, WorkManager for downloads that survive the app closing, iOS devices without Apple Intelligence. |
| 54 | **Offline maps can be cut on the phone (`MAP_EXTRACTS=device`).** The container approach stays (default `server`), but the owner won't pay for Containers until there are paying users. In device mode the Worker sends the trip's areas (`device_tiles`) and the planet URL; the app plans each extract from the planet's directories, fetches only those tiles with merged range requests (≤4 MB, 6 in flight), and writes a clustered PMTiles v3 file (`lib/services/pmtiles.dart`), hashed locally so reuse and companion handoff work unchanged. Output matches `pmtiles extract` tile-for-tile (Sequoia z15: 1,021 tiles; Bay Area z15: 81 MB in ~7 s, 107 requests). | Owner direction (2026-10-04): personal project, no fixed costs before revenue. The agent can't do it (most MCP clients have no shell; MCP can't carry 100 MB files; uploads would be unverifiable), the phone can. Trade-offs: needs the app in the foreground while the map builds (no background session for range requests), and many devices reading build.protomaps.com directly (check their terms; the R2 mirror is the fix). |
| 55 | **Online map in the app, on by default, with a Settings switch.** `/download` always names an online basemap (`online_tiles_url`: `ONLINE_TILES_URL`, else the planet maps are cut from), for every plan. The app's loopback server proxies range reads at `/__waypack/tiles/{trip}/online.pmtiles` (Range required, so the planet is never streamed whole; 502 when offline), keeping the bundle CSP at `connect-src 'self'`. Downloaded extracts are tried first per tile, so the online map only fills in outside them or when none exist. Settings → Maps → "Use online map" (off = downloaded maps only, e.g. to save roaming data). | Owner request (2026-10-04). Before this, the app had the plumbing but never set the URL, so trips without an offline map showed places on a blank background. |
| 56 | **Files live in Supabase Storage, not R2.** Bundles, uploads, previews and shares go to the private `waypack` bucket (migration `20261009000000_file_storage.sql`), written only by the Worker with the service key. `src/lib/bucket.ts` implements the slice of R2's bucket API the code used (head/get with range/put/delete/list), so call sites didn't change; Storage's list is one folder deep, so a service-role-only `storage_list` RPC lists keys by prefix. R2 remains only for container mode's optional planet mirror (`BASEMAP`). | Owner direction (2026-10-04): data and files in one place. Trade-offs: Supabase free plan caps files at 50 MB (bundles are ≤ 25 MB) and 1 GB total, and egress counts against Supabase's quota where R2's was free. Server-mode map extracts can exceed 50 MB; they need Pro if the container comes back. |
| 57 | **Mac DMGs ship as GitHub release assets** (supersedes #36). `release_mac.sh --notarize --upload` creates release `mac-v<version>` on the public repo with the DMG as `Waypack.dmg`; the Worker's `/download/mac` is a 302 to `github.com/<repo>/releases/latest/download/Waypack.dmg` (`MAC_RELEASES_REPO`, default tianhaoz95/waypack). No storage, no `latest.json`, no API calls. | Owner direction (2026-10-04). The fixed asset name keeps one stable link; release history and checksums live on GitHub. Only Mac releases use GitHub releases (phones ship through the stores), so "latest" stays the Mac build. |
| 58 | **"Scrapbook" home screen.** Trips are polaroids on kraft paper: upcoming in a 2-up grid (more columns on wide screens) with washi tape and handwritten captions (Caveat, OFL, bundled in `assets/fonts`), past trips in a smaller 3-up "Remember when…" grid.
